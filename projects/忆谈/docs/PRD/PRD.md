## 1. 原始需求（逐字保留，不改写）

面向老人的微信语音回忆录服务:售卖服务后,老人通过微信电话与AI多次对话,口述一生经历,AI访谈、整理,最终交付一本定制化回忆录

**用户补充原话（2026-11-05）：**

1. 产品名：待确认
2. 一个卖了服务之后，给老人使用，可以接到微信中，让老人通过打微信电话，和ai进行沟通，吐露出自己一生的经历，最终汇总成一本回忆录的产品
3. 给有记录需求（回忆录）的老人，比如记录他从小到大的一生，现在有人上门或者通过电话，以及通过子女进行口述等途径实现，你可以先检索了解一下，前两年很火，银发经济
4. 通过多次的对话，沉淀出一个老人的一生，然后交付一本定制化的回忆录

## 2. 需求拆解

### 2.1 目标

- **一句话**：让普通老人只需「开口聊天」，经过多次对话，就能拥有一本属于自己、内容真实、可传给家人的定制回忆录。
- **成功标准**：见第 5 节。

### 2.2 用户（两类人，不是一类）

| 角色 | 是谁 | 要什么 | 与产品的关系 |
|---|---|---|---|
| **使用者** | 有记录需求的 **60 岁以上**老人；V1 定位**普通话，或语音识别效果较好的方言**（具体方言待确认）【V2 新增】 | 有人听我讲、讲完有成果、操作不要难 | 开口讲，几乎不操作 |
| **购买者 / 决策者** | 多半是子女（待确认） | 给父母留下记忆、尽孝心、省心省力 | 下单、建档、提供背景、审阅、收书 |

- 产品本质上是**一份送给老人的礼物**：子女购买、老人受益；家属与老人对内容的意见基本不会冲突，**若冲突，以老人为准**【V2 新增】。
- 人机比：1 位老人对应 1 个 AI 访谈者，多次异步会话；一个订单配 1 位家属管理者。
- 交互形态：**同步语音**（老人与 AI 通话）+ **异步审阅**（家属看章节、提意见）。

### 2.3 核心闭环（一次完整的「输入 → Agent 行为 → 交付物」）

```
购买服务 → 家属建档（老人基本信息、家人名字、想聊的方向、老照片）
   → 老人开启通话（接入形态见 6.1，待确认）
   → AI 访谈者开场（说明身份 + 征得录音同意）→ 20~30 分钟对话，边听边追问
   → 通话结束：转写、清洗口述、抽取人物/事件/时间，更新「记忆图谱」
   → AI 写作者生成本次章节草稿（只扩写，不杜撰，每句可溯源到原话）
   → 家属/老人审阅、补充或删改 →（可选）真人编辑审校
   → 下一次通话：AI 回顾上次内容，补缺口、问没讲完的人和事
   → 累计达到章节覆盖度后，汇总排版、装帧 → 交付回忆录
```

### 2.4 交付物

- **核心**：一本定制化回忆录（形态待确认：电子版 / 精装实体书 / 二者兼有）。
- **可能的延伸**（待确认是否纳入 V1）：访谈音频存档、家族关系图、人生大事年表、章节朗读（可让老人听到「自己的故事」）。
- 每次通话后的**中间交付**：章节草稿，用于让家属和老人持续看到进展、保持动力。

### 2.5 边界（初步，详见第 4 节）

- 不是「数字复活」「AI 灵堂」等产品；定位是记录**还在世的老人**自己的口述。
- 不是通用聊天陪伴；AI 的任务是访谈和记录，不做医疗/法律/理财建议。
- 不替老人编造任何没说过的事实。

### 2.7 微信接入的可行性（关键风险，必读）

据微信开放文档与腾讯云文档检索结果（2026-11-05）：

- 微信**没有**开放「AI 机器人主动拨打微信语音电话给用户」或「AI 作为联系人接听个人微信来电」的官方能力。
- **可行路径 A（推荐验证）**：做一个**企业主体的微信小程序**，老人点一个大按钮发起「AI 通话」；小程序用实时音视频（如腾讯云 TRTC）进房，云端 AI 智能体加入房间，实现流式语音识别、可打断、语音合成。**AI 不能主动来电，老人（或家属）要主动点开。** 该能力需要企业类小程序并通过类目审核，不支持个人主体，也不支持企业微信小程序；切后台/锁屏会断流。
- **路径 B**：微信官方「小程序音视频通话（硬件版）」可让设备主动呼叫用户微信并有强提醒，需要把 AI 服务包装为已认证设备，门槛高，适用面待评估。
- **路径 C**：不走微信通话，改为 **AI 外呼老人普通手机/座机**（海外同类产品的主流做法），老人接电话即可；需要云呼叫能力与相应的外呼资质，**国内合规要求待核实**。
- **路径 D**：微信里发**语音消息**（异步一问一答）。体验最弱，但最容易做；可作兜底。
- 绕道用「个人微信号机器人」自动接电话/发消息属于违反平台规则的灰色做法，**不建议**。

> 这是需求里最需要你拍板的一点，见 6.1。

### 2.10 差异切口与待验证的技术点（V3 新增，2026-11-06）

**用户一手体验（2026-11-06）**：用户亲自体验过小鹿光年，感受是**「完全一问一答，很难有和真人互动的真实感，像在回答问题」**。据此，V1 的差异切口之一定为**「像真人聊天的长对话」**（见 FR24~FR27）。

> 说明：这是用户的主观体验，AI 没有实际体验过该产品；官方资料称其为语音实时对话 + 动态追问，但「一问一答」的割裂感来自轮流发言的交互与每轮以提问收尾的访谈方式，二者不矛盾。

**技术现状（2026-11-06 检索，均来自官方文档或厂商自述，未经我们实测）**

| 方案 | 已知能力 | 已知限制 |
|---|---|---|
| 豆包实时语音 3.0（Seeduplex，火山引擎） | 全双工端到端；用户开口可打断；可调用工具；WebSocket 接入 | 官方计费页未单列价格；系统指令与上下文合计上限 12K token；**方言支持情况未查到**；旧版接口仅标注支持中文和英文 |
| OpenAI gpt-realtime | 语音到语音；语义 VAD（不同档位最长等待约 2/4/8 秒）；静音不计费 | 国内网络一般连不上；老人声音出境有合规问题 |
| 开源：SoulX-Duplug、KE-SemanticVAD | 区分「附和 / 没说完 / 说完了 / 打断」，用于给现有系统加全双工能力；SoulX-Duplug 延迟约 250ms | 是零件，不是成品；需自行集成 |

| 编号 | 要验证的事 | 通过标准（建议，待确认） | 失败时的备选 |
|---|---|---|---|

| T5 | **附和不被打断**：老人说「嗯」「对」时 AI 是否仍继续 | 附和不触发打断 | 加语义门控模块 |

### 2.9 「文字模拟访谈」的澄清（2026-11-05 用户反馈）

- **老人侧永远不用文字**：对老人只有语音（通话或语音消息），产品形态上**不提供「打字对话」作为老人的使用路径**。
- 开发阶段用的「文字模拟访谈」**只是内部测试台**：由开发者（或 AI 扮演的老人）打字，用来验证访谈追问、记忆抽取、章节写作的逻辑，**不交付给用户**。
- 因此 V1 的核心引擎输入抽象为「一段口述转写文本」，上游由语音识别提供；这样引擎既能被文字测试台驱动，也能被真实语音渠道驱动。

### 2.8 约束（已知 / 待确认）

| 项 | 状态 |

| 并发 | 待确认（取决于首批规模） |
| 合规 | 涉及老人声音（属敏感个人信息）、录音、AI 生成内容标识、生成式 AI 备案等，**待核实**；见第 4 节 |
| 成本上限 | 待确认（单本成本 = 语音识别 + 模型 + 语音合成 + 通话流量 + 人工 + 印刷） |
| 可用模型 | 当前未配置 API Key；模型与语音服务供应商待选 |
| 方言 | V1 定位普通话，或语音识别较好的方言；其他方言不在 V1 范围【V2 新增】（此为已确认的约束） |
| 技术栈 | **未确定**（6.15 开发角色待确认）；方案中出现的具体语言/框架仅为候选建议，不是决定（V3 澄清） |

## 4. 边界与红线

**必须做到（红线）**

1. **身份透明**：每次通话开场声明自己是 AI，不冒充真人。
2. **知情同意**：录音与使用必须由老人**本人**明确同意；子女代为下单不等于老人同意。老人声音属于敏感个人信息，需按《个人信息保护法》取得单独同意（具体条款**待法务核实**）。
3. **只扩写、不杜撰**：不得编造老人没说过的事实；AI 补充的背景资料必须单独标注；不确定的内容进入「待核对」，不直接写进书稿。
4. **老人可随时拒绝**：任何话题可跳过；说「不想讲」立刻转移；说「别再打了」永久停止。
5. **不索取敏感信息**：不问、不记银行卡、密码、验证码、身份证号、详细住址、病历；如老人主动提到则转移话题，且不写入稿件。
6. **不给建议**：不提供医疗、法律、投资建议；老人问到时礼貌说明不能回答并建议咨询家人或专业人士。
7. **情绪与安全**：老人明显痛苦、混乱，或出现自伤、求助信号时，结束访谈，通知预留的家属；不做心理咨询。
8. **隐私与数据主权**：数据仅属于该家庭；可导出、可删除；声音、照片、文稿加密存储，访问留痕。
9. **第三方隐私**：涉及他人（尤其是未成年人、已故者、争议事件）的内容，成书前需家属确认是否保留。
10. **敏感历史话题**：老人讲述历史运动、政治等敏感经历时，如实记录为老人个人叙述，成书与分享前按平台内容安全规则和家属意愿处理（具体规则**待确认**）。

11. **不编造 AI 的个人经历**（V3 新增）：为了让对话像真人，AI 可以共情、复述、感叹，但**不得说「我小时候也…」「我也经历过…」之类的虚构个人经历，不得假装与老人有共同经历**；被问到时坦诚说明自己是 AI。
12. **不因追求自然而放松红线**（V3 新增）：全双工自然对话下，第 1~10 条红线（AI 身份声明、录音同意、不索取敏感信息、不给建议、情绪异常处理等）同样生效；实时语音模型必须能被这些规则约束，**做不到的模型不得用于面向老人的通话**。

**降级要求（V2 补充）**：任一环节失败都要有明确降级路径，且不得因失败而杜撰内容——包括语音转写失败、记忆抽取失败、写章节失败、整本排版失败、印刷下单失败、通话中断/超时。失败时保留原始音频与已有成果，标记状态，通知家属，允许重试或转人工。每一类失败都要在方案里有对应的降级说明，**包括印刷下单失败、事实核对队列写入失败、实时语音通道中断（V3 澄清）**。

**不做什么**

- 不做「数字复活」「AI 灵堂」「模仿老人声音」等产品。
- 不做通用陪聊、健康监护、紧急呼救（避免被误认为安全监护产品）。
- 不做公开发布/社交传播（V1 默认私有，仅家庭内分享）。

### A. 会决定架构的关键问题

**6.1 老人「打微信电话」怎么实现？** 🔴 最优先

微信不提供 AI 接听/拨打普通微信电话的官方接口（见 2.7）。请在以下路径里选：

- A. **小程序内一键语音通话**（企业主体小程序，老人点按钮，AI 实时对话）——最贴近「在微信里」，需企业资质与类目审核，AI 不能主动来电
- B. **微信硬件 VoIP**（AI 包装成设备，可强提醒来电）——门槛高
- C. **AI 打手机/座机电话**——老人最省事，国内外呼合规待核实，不在微信里
- D. **微信语音消息**（一问一答，异步）——最易做，体验较弱，可当兜底
- E. 组合（例如 A 主 + C 兜底）

回答（2026-11-05）：**小程序能实现就用小程序**；用户注意到市面上有「让 DeepSeek 接入微信」的做法，希望考虑类似途径。
→ AI 分析：那类做法多数是 ① 个人微信号机器人（用第三方工具/协议接管个人号，只能收发文字、语音消息，不能实时通话，且违反微信规则、有封号风险）；② 公众号 / 企业微信 / 微信客服（官方，但只能做消息交互，不是实时电话）；③ 小程序内嵌 AI 对话（官方）。它们**都不能让老人「像打微信电话一样」和 AI 实时对话**。因此决策为：
- **主路径**：小程序一键语音通话（路径 A）。
- **兜底路径**：在小程序/公众号内的语音消息对话（路径 D，同一套后端可复用）。
- **不采用**：个人微信号机器人（封号、合规和稳定性风险；不适合要收费、要保存老人声音的服务）。
- **保留观察**：AI 外呼手机（路径 C），等 6.10 的合规结论后再决定是否加入。
- **开发顺序建议**：先用「文字模拟访谈」跑通访谈与写作逻辑（不依赖微信），再接语音与小程序。
